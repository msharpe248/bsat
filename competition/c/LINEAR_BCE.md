# Linear tautology checks for blocked-clause elimination

Blocked-clause elimination (BCE) previously called the quadratic cross-parent
literal comparator and charged the product of parent lengths before each check.
Long overlapping clauses could consume the complete preprocessing budget without
eliminating a clause. BVE already has a bounded linear resolution-pair routine.
This change exposes a small boolean wrapper and uses it for BCE as well.

The routine marks non-pivot variables with their literal polarity, finds opposite
marks, and clears every touched mark before returning. It owns the otherwise idle
minimizer scratch during root preprocessing. There is no new persistent array or
per-pair allocation. False means either non-tautological or interrupted/exhausted;
BCE treats either as failure to establish that the candidate is blocked, so it
cannot delete on an incomplete check. The cross-only quadratic helper remains
available as an independent regression oracle. Runtime parents are canonical
(non-tautological) solver clauses, for which the two predicates agree.

Work now counts parent literal visits and mark cleanup rather than the product
of parent lengths. Cleanup is mandatory and may carry work beyond a cutoff by
the number of touched variables, as in the existing BVE routine. CPU polling
uses that routine's existing cached-clock policy. BCE witness copying, allocation
and deletion are unchanged; this is not a complete preprocessing latency bound.
With a fixed work budget, the candidate can complete more BCE work and therefore
change search order. Ordinary default search remains unaffected because BCE is
opt-in with `--bce`.

## Discovery and correctness evidence

The [discovery probes](benchmark_results/linear-bce-discovery-20260907.json)
compare preprocessing options on the larger hardware-verification input. All
five profiles remain UNKNOWN at ten solving CPU seconds. A larger SCC budget
completes 1,624 substitutions and 5,072 rewrites in 2,940,465 work units, without
a solve. These counters led to code review rather than a default budget change.
The source review found the remaining quadratic BCE check; this milestone does
not claim to solve the hardware-verification case.

The new `test_bce_linear.c` checks **6,561 canonical clause pairs** against the
independent quadratic oracle, including absent/shared/opposite tail variables
and pivots placed at the end. It additionally tries **111,537 work cutoffs**,
asserting that successful tautology reports agree with the oracle, completed
checks agree in either direction, and scratch marks are always clear. A
1,000-variable integration case requires both original clauses to be eliminated
within 10,000 preprocessing work units and validates the reconstructed model.

The [old/new budget check](benchmark_results/linear-bce-budget-20260907.json)
uses the generated 1,000-variable overlap CNF and the same 10,000-work allowance.
The baseline removes zero blocked clauses; the candidate removes two. Both
produce independently checked models against the original CNF. This is a
concrete improvement in work completed per budget, not a gained SAT solve.

Both builds pass all **36 C test executables**. Each build independently
passes 2,967 validation solves (seed 20261029), with truth-table answers, original
SAT models and text/binary UNSAT proofs checked using external drat-trim. Both builds pass 42 short-deadline cases, with maximum observed CPU
overrun 0.000 seconds in release and 0.001 seconds in ASan/UBSan debug.

## Performance

The [overlap comparison](benchmark_results/linear-bce-overlap-20260907.json)
uses 1,000, 5,000 and 10,000-variable two-clause formulas generated by the existing
resolution corpus script. Both solvers enable BCE, disable probing and receive
one billion preprocessing work units, ten solving CPU seconds and a 15-second
wall limit. Three repetitions per size/profile use seed 20261030. Both verify
all **9/9** original models, with zero errors. Median process CPU:

| Variables | Quadratic | Linear | Quadratic / linear work |
| --- | ---: | ---: | --- |
| 1,000 | 0.002940 s | 0.002609 s | 1,002,000 / 4,999 |
| 5,000 | 0.015266 s | 0.005009 s | 25,010,000 / 24,999 |
| 10,000 | 0.051140 s | 0.007928 s | 100,020,000 / 49,999 |

At 10,000 variables this is approximately **6.45 times faster** process CPU,
including parsing, search, reconstruction and output. This is a synthetic
long-clause result, not an isolated function timer or general competition gain.
Ten selected counters match across all six runs per input: decisions,
propagations, conflicts, restarts, learned clauses/literals, deleted clauses,
blocked clauses, garbage collections and reductions. Both remove two blocked
clauses. Work intentionally changes. Mean wall PAR-2 is 0.033650 versus 0.008512
seconds; maximum process RSS is 4,653,056 versus 4,702,208 bytes.

The [larger competition screen](benchmark_results/linear-bce-large-20260907.json)
reuses the eight-input larger manifest. Both profiles enable BCE, disable probing
and receive ten million preprocessing work units, three solving CPU seconds and
a five-second external wall limit. Two repetitions use seed 20261031. Both verify
**2/16**, the two multiplier-verification runs, with zero errors. No solves are
gained or lost. Mean wall PAR-2 is 8.95460 versus 8.96763 seconds; maximum process
RSS is 81,920,000 versus 81,854,464 bytes. Some runs hit the external wall limit
before the internal CPU limit and have no final counters; missing counters are
not zero. These measurements do not establish a broad speedup or parity.

Retain the linear BCE integration for the demonstrated long-clause improvement
and extra useful work completed under a fixed budget. Keep BCE opt-in. The
hardware-verification target remains unsolved, and broader competition
performance and soundness remain open. No default-policy change is justified.

All performance runs are serial and follow terminal completion of builds,
validation and deadline checks. Models and proofs are independently verified
outside solver timing. Process CPU includes startup, parsing and output; the
internal limit excludes parsing. Unverified answers receive twice the external
wall limit as PAR-2. Executable and checker hashes match after measurement. The
inputs are development material, not a held-out evaluation.

## Reproduction

```sh
make -C competition/c all test
make -C competition/c all test MODE=debug
python3 competition/c/tests/validate.py --solver competition/c/bin/bsat --checker /tmp/bsat-drat-trim --cases 30 --seed 20261029
python3 competition/c/tests/validate.py --solver competition/c/bin/bsat_debug --checker /tmp/bsat-drat-trim --cases 30 --seed 20261029
python3 competition/c/tests/check_deadlines.py --solver competition/c/bin/bsat
python3 competition/c/tests/check_deadlines.py --solver competition/c/bin/bsat_debug
python3 competition/c/tests/generate_elim_resolution_corpus.py /tmp/bsat-linear-bce-corpus
```

Build `b75b86e` as the baseline and preserve its executable separately. Raw
records retain exact solver commands and binary/input/checker hashes. The existing
overlap generator is unchanged and reused for BCE measurements.

For the overlap comparison, pass the generated manifest to `tests/benchmark.py`,
use `--bce --no-probing --preprocess-budget 1000000000 --time 10` in both solver
templates, and use `--timeout 15 --repeats 3 --seed 20261030`. For the larger
screen, use the committed larger manifest and the limits and seed above.
